# 需求澄清 Skill

不要拿着模糊需求直接写代码，也不要一次性抛出十个开放式问题让用户填空。
你的职责是：**先摸清系统现状，再以"选择题"的方式一轮轮引导用户做决策，最终产出一份详细设计方案。**

```
模糊需求 → [阶段0] 摸底现状 + 需求定型 → [阶段1] 多轮澄清（每轮1问 + 2-3个推荐方案）
        → [阶段2] 自检 + 输出设计方案 → 用户确认 → （可选）进入实现
```

---

## 阶段 0：摸底现状与需求定型

### 摸底代码库

提问之前先探索代码库：技术栈与分层方式、与需求相关的现有模块和数据表、既有约定（错误处理、鉴权、API 风格、消息队列等）、硬约束（数据库、部署方式、第三方依赖）。

**规则：凡是能从代码里查到的，绝不去问用户。** 摸底的产出是：后续每个选项的优劣分析都必须落到"当前系统"上，而不是泛泛而谈。

### 需求定型

判断需求的**类型**（决定问什么）和**规模**（决定问多少）：

| 类型 | 澄清重点 |
|---|---|
| 新功能 | 目标 → 范围 → 核心行为 → 数据 → 接口 → 集成 → 非功能 → 上线（无关维度跳过） |
| 已有功能改造 | 改动边界、兼容性、受影响的调用方、迁移 |
| 性能优化 | 当前瓶颈证据、目标量级、可接受的取舍（一致性/成本） |
| 技术重构 | 动机、范围边界、行为不变的验证手段、分步策略 |
| 问题修复 | 复现路径、预期行为、影响面、是否治本 |

| 规模 | 判断标准 | 轮次 | 产出 |
|---|---|---|---|
| S | 单模块、改动点明确 | 0-1 | 不出文档，确认一句后直接动手 |
| M | 2-4 个模块、2-3 个关键决策点 | 2-4 | 精简设计（省略不适用章节） |
| L | 跨系统/新子系统/有数据迁移 | 4-6 | 完整设计文档 |

### 首轮回复

摸底完成后，**在同一条回复里**完成三件事：

1. 用 3-5 句话同步现状（相关模块、可复用的东西、关键约束），让用户能纠正误解；
2. 一句话说明类型/规模判断，并给出**预计提问轮数**；
3. 直接提出第一个问题。

若摸底发现需求与现状有根本冲突（所需能力当前架构完全不支持），第一轮就把冲突作为问题抛出，不要憋到最后。

## 阶段 1：多轮澄清

**首次提问前，先读本目录下的 `example.md`，严格模仿其中的问题格式与选项质量。**

### 提问节奏

- 每轮只问 1 个问题（强相关时最多 2 个）。先问"答案会改变整体架构"的，后问"只影响局部实现"的。
- 每个问题标注进度 `问题 2/4`，结尾一行预告下一题主题。
- 后续问题的选项必须**基于已确认的决策**构建，不要给出与已定结论矛盾的选项。
- 不要问用户无法回答的实现细节（如"乐观锁还是悲观锁"）——这类自己按现状决策，写进决策记录即可。提问是为了收敛，不是免责。

### 选项质量要求

每个问题给 **2-3 个具体候选方案** + ⭐ 推荐（完整示范见 `example.md`）：

- 具体可执行，点名当前系统的真实文件/模块；禁止"简单做 vs 复杂做"式空洞选项。
- 选项间要有真实权衡差异（复用 vs 新建、同步 vs 异步、改表 vs 加表）。某决策点只有一个合理做法时不造伪选项——直接作为既定结论写进决策记录，附一句理由。
- 代价用受影响模块数和改动侵入性描述，不估天数。
- 推荐理由必须引用现状（"因为当前系统…"），不套通用最佳实践。

### 用户回应的处理

| 用户回应 | 处理 |
|---|---|
| "你定" / "都行" | 直接采纳推荐项继续，不再确认 |
| 自己给了新方案 | 采纳；若与系统现状或既有约定冲突，当场指出再确认 |
| 回答推翻了之前的假设 | 明确列出受影响的已有决策并重新确认，不默默改 |
| 要求修改某条已确认决策（"改第 2 条"） | 更新该决策，检查其余决策是否连锁失效，失效的重新问 |
| "别问了 / 赶时间 / 直接出方案" | 切换**打包模式**：剩余决策点连同推荐一次性列出，请用户"默认全按推荐，有异议单独指出"，然后进入阶段 2 |

### 决策记录

从第二轮起，每轮提问前展示累计决策：

```
📋 已确认（2/4）
1. 送达方式：站内信轮询（方案 A ⭐）
2. 触发来源：评论 + @提及（用户自定义）
```

同时同步写入 `docs/design/.clarify-<需求名>.md`（目录不存在则创建），防止长对话上下文压缩后丢失决策；阶段 2 完成后删除。

### 终止条件

关键维度有结论、或剩余问题不影响整体设计（转为待定项）、或用户喊停——即进入阶段 2。轮次超出规模上限时立即切换打包模式收尾。

---

## 阶段 2：自检并输出设计方案

### 输出前自检

- [ ] 每个已确认决策都在文档中有对应落点，无遗漏、无矛盾
- [ ] 改动清单里点名的文件路径在代码库中真实存在（新建文件除外）
- [ ] 待定项都标注了默认处理方式，不阻塞开工

### 文档结构

写入 `docs/design/<需求名>.md`（无仓库环境则直接回复输出）。M 规模省略不适用章节，不写空章节凑数。

```markdown
# <需求名> 设计方案

## 1. 背景与目标        —— 解决的问题、目标用户、成功标准
## 2. 范围              —— 本期做什么 / 明确不做什么（non-goals）
## 3. 决策记录          —— 每个决策点的结论与理由，保留被否掉的方案名
## 4. 现状分析          —— 相关现有模块、可复用能力、关键约束
## 5. 总体设计          —— 方案概述、模块关系图（mermaid）、关键流程
## 6. 详细设计          —— 数据模型（字段定义）、接口（签名+示例）、
##                        模块改动清单（逐文件）、关键逻辑（伪代码）
## 7. 非功能设计        —— 性能、安全/权限、兼容性、失败处理
## 8. 上线方案          —— 迁移、开关、回滚（如适用）
## 9. 验收标准与测试要点 —— 可勾选清单（每条对应一个决策或核心行为）、边界场景
## 10. 待定项           —— 后续确认的问题，标注默认处理方式
```

输出后询问：**"方案确认后是否直接开始实现？"** 确认前不动手写业务代码。确认后按"模块改动清单"顺序执行，实现中发现设计遗漏时回填文档。

---

## 注意事项

- 全程使用用户所用的语言。
- S 规模需求不走流程：确认一句理解后直接动手。
- 如果用户其实是在提问或讨论（而非要求实现），给出分析即可，不要启动澄清流程。
