# 示范：一轮标准的澄清提问

背景：用户在一个 Express + PostgreSQL 单体项目中说"加个通知功能"。摸底后发现：REST 风格路由在 `src/routes/`，无 WebSocket 基础，前端有统一的 header 组件。

---

### 问题 1/4：通知的送达方式

这决定了是否要引入新的基础设施，是整个方案里影响最大的决策。

**方案 A：站内信（落库 + 前端轮询）** ⭐ 推荐
- 做法：新增 `notifications` 表，按现有 `src/routes/` 的 REST 风格加两个接口（拉列表、标记已读），前端在现有 header 组件加铃铛入口
- 优点：零新依赖，改动集中在 3 个文件
- 代价：非实时（轮询间隔内有延迟）

**方案 B：站内信 + WebSocket 实时推送**
- 做法：方案 A 基础上引入 socket.io，在 `app.ts` 挂载，通知产生时主动推送
- 优点：实时送达
- 代价：引入新依赖和长连接管理；项目没有 WebSocket 基础，nginx 配置也要改

**方案 C：邮件通知**
- 做法：接入 SMTP/SendGrid，事件发生处直接发邮件，不落库
- 优点：无前端改动
- 代价：依赖外部服务和密钥；用户无法站内回看历史

推荐理由：当前系统没有实时性要求的先例，方案 A 改动最小，且不排斥后续升级到 B。

> 回复方案字母即可；也可以说"你定"由我按推荐执行，或补充你自己的想法。
> 下一题预告：通知的触发来源（哪些事件产生通知）。

## 这个示范体现的要点

1. **标题即决策点**，一句话说清为什么它重要。
2. 每个方案的"做法"**点名真实文件/模块**（`src/routes/`、`app.ts`、header 组件），不是抽象描述。
3. 方案之间有**真实权衡**（零依赖 vs 实时性 vs 免前端改动），不是"简单做 vs 复杂做"。
4. 代价用**改动侵入性**描述（3 个文件、要改 nginx），不估天数。
5. 推荐理由**引用现状**（"当前系统没有实时性要求的先例"），不套通用最佳实践。
6. 结尾固定给出**回应方式提示 + 下一题预告**。
